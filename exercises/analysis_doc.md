## 1. 解析計画書の書き方・ワークフロー

解析計画書は、次のステップで組み立てます。先にステップ順に条件を絞り込むことで、「とりあえずコード」「後で詰まる」を防ぎます。<br>
ターゲット：「福島県浜通り（相馬市・南相馬市）の農地における作付変化と休耕地検出」

| Step | 記入内容 | 主な観点 |
|------|----------|---------|
| **Step1 課題** | ターゲットの解析は誰の・どんな課題を解決するか, なぜターゲットのような解析を行うのか, 課題背景 | 非専門家（現場） |
| **Step2 物理仮説** | なぜ光学＋SARで判別できるか。季節イベント（例: 5月の水張り・8月の繁茂・秋の収穫）をどの観測量でどの時期に検出するか | 専門家 |
| **Step3 データ** | 使用データと前処理（S-2 / S-1 / 筆ポリゴン、CRS・軌道・dB） | 専門家 |
| **Step4 手法** | 解析方法（時系列 / 変化検出 / 特徴量スタック / ML）とその選定理由、期待する出力 | 専門家 |
| **Step5 検証・社会実装** | 検証方法・成功の定義（混同行列・誤分類の検出）と、自治体等の非専門家が使える形（確信度・ダッシュボード・費用対効果）。**社会実装の6項目**（①誰が使う②何を減らす③何を出す④必要な精度⑤業務削減目標（要確認率 r で試算）⑥失敗時の影響） | 両方 |

> **8/20 メンターレビューに向けて:** Step5 の最後に **「メンターへの質問（1〜2点）」** を「状況＋仮説＋確認したいこと」の3行で書きます。

**各ステップを書くときの注意**
- 非専門家観点の欄は、**結論ファーストで「誰のために何を解決するか・コスト」**を中心に書く。
- 専門家観点の欄は、**物理的な根拠（バンド・散乱機構・CRS・軌道など）**を中心に書く。

## 2. AIへの5つの問い（批判的思考チェック）

生成AIが返したコード・回答をそのまま信じる前に、必ず次の5つを疑います。**エラーが出ないこと＝正しいコードではない**ため、この5点をコードの該当行と数値で確認します。

1. **単位は正しいか？** … dB（S1_GRD は既にdB）／反射率／線形？
2. **バンド・偏波は正しいか？** … NDVI なら B8 & B4、SAR なら VV / VH？
3. **座標系（CRS）は揃っているか？** … EPSG:32654 / JGD2011 などは一致？
4. **軌道方向・観測モードは統一されているか？** … ASC / DESC は統一、観測モードは IW？
5. **観測時期・雲量は妥当か？** … 季節サイクルに合うか、雲フィルタはある？

**確認方法:** コードの該当行を特定 → GEE Code Editor の **Inspector** でピクセル値計測 → 物理的根拠（スペクトル・散乱機構）と照合。

## 3. 専門家 / 非専門家への説明（共通項と違い）

| | 専門家（メンター・技術レビュー） | 非専門家（自治体・農政・意思決定者） |
|--|--|--|
| 強調 | **物理的根拠**・不確実性・再現性 | **結論ファースト**・現場価値（見回りコスト削減等）・費用対効果 |
| 伝え方 | 「なぜそのバンド・軌道・CRSか」をコードで追える形で | 図・ダッシュボード・1行の結論 |
| **共通** | どちらにも… **①目的（誰の何の課題）を明確に ②データの出どころ・信頼度を伝える ③誤差と限界を隠さない ④簡単な言葉で説明できる** |

> 「どちらか一方」でなく両方想定する。同じ結果を根拠（専門）と価値（非専門）に使い分けるのがデータフュージョンの2軸。

## 4. ブランチの使い方（camp-[チーム名]）

このリポジトリのブランチは用途ごとに分かれています（詳細は `README.md`・`WORKFLOW.md`）。

| ブランチ | 用途 | 作業ディレクトリ |
|----------|------|----------------|
| `main` | 教材（演習テンプレート・各種ガイド） | — |
| `submissions` | 個人演習の提出 | `submissions/individual/<名前>/` |
| `prelim-a` / `prelim-b` | 事前学習（A/B群）のチーム演習 | `submissions/prelim/team-a/` 等 |
| **`camp-alpha` / `camp-beta` / `camp-gamma`** | **合宿プロジェクト（解析計画書・解析コード・発表資料）** | `submissions/camp/team-alpha/` 等 |

**合宿プロジェクトでは、自分のチームの `camp-*` ブランチで作業し、成果物を `submissions/camp/` 配下に置きます。** 他のチームのブランチにはコミットしないこと。
